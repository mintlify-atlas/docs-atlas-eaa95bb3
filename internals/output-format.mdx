Every time the Nano compiler runs successfully, it produces a complete, self-contained NASM win64 assembly program. The output file requires no linker scripts, no extra object files, and no external dependencies beyond `kernel32.lib` — it is a ready-to-assemble text file that reproduces the full behaviour of the original Nano source. The file is written by the back-end (`nlang_writer.nasm`) into a 1 MB in-memory buffer and flushed to disk as `<input>.nasm` (for example, `script.n` → `script.nasm`).

## File Structure

The generated file follows a fixed section order that NASM requires for correct assembly:

<Steps>
  <Step title="Header boilerplate">
    The file always opens with the standard win64 preamble emitted from the `s_header` string constant. This declares the bit width, the default addressing mode, the external symbol, the entry point, and the stack alignment prologue.
  </Step>
  <Step title=".bss variable declarations">
    `num`, `str`, and `list` variables are declared as uninitialised qword or block reservations. Each declaration switches to `section .bss`, emits the label and the `resq` or `resq LIST_CAP + 1` directive, then switches back to `section .text`.
  </Step>
  <Step title=".data lstr declarations">
    Long-string (`lstr`) variables are declared as initialised data. Each one switches to `section .data`, emits the length as a `dq` and the content bytes as a `db` list, then switches back to `section .text`.
  </Step>
  <Step title=".text main logic">
    Variable initialisers and all compiled statements appear inline in `section .text`, immediately after the relevant variable declaration. The compiler interleaves section switches with the logic so each variable's declaration and initialisation code appear together in the output.
  </Step>
  <Step title="Footer">
    `s_footer` appends the clean exit sequence after the last compiled statement.
  </Step>
  <Step title="Runtime helpers (if needed)">
    If any list operations or string indexing were used, the shared `rt_err_full` / `rt_err_range` preamble is appended first, followed only by the individual helper routines that the program actually calls.
  </Step>
</Steps>

## Header Boilerplate

The `s_header` string is emitted verbatim at the start of every generated file. It produces the following NASM source:

```nasm
; Generated by the Nano compiler. Assemble with:  nasm -f win64 <this file>
bits 64
default rel

extern ExitProcess
global main

LIST_CAP equ 1024               ; entries per list

section .text
main:
    sub  rsp, 40
```

The `sub rsp, 40` establishes a 40-byte stack frame (32 bytes of shadow space plus 8 bytes to re-align the stack, since the `call` to `main` pushed a return address that left `RSP` as `8 mod 16`). The `LIST_CAP` constant is always defined, even in programs that contain no lists.

## Variable Label Naming

Every variable is emitted with a `v_` prefix in front of its Nano name. This prevents collisions with NASM keywords and runtime helper labels.

| Nano name | Generated NASM label |
|-----------|---------------------|
| `x` | `v_x` |
| `counter` | `v_counter` |
| `__pkg_name` | `v___pkg_name` |
| `my_list` | `v_my_list` |

The prefix is hard-coded as the string `v_` in the `s_vpre` data constant and is prepended by `emit_label_p` before every label that appears in the output.

## `num` and `str` Variables

Scalar numeric and short-string variables are placed in `.bss` as a single uninitialised qword. If the declaration includes an initialiser, one or two instructions are emitted in `.text` immediately after the `.bss` declaration to store the value.

**Without an initialiser (num):** the slot is zero-initialised by the OS loader — no `.text` instructions are needed.

**Without an initialiser (str):** the default value `'0'` (ASCII 0x30) is always written, because an uninitialised `str` should hold the character `'0'`, not a zero byte.

**With a literal initialiser:**

```nasm
section .bss
v_x:  resq 1
section .text
    mov  rax, 42
    mov  [v_x], rax
```

**With a value-expression initialiser** (e.g. copying from another variable):

```nasm
section .bss
v_copy:  resq 1
section .text
    mov  rax, [v_source]
    mov  [v_copy], rax
```

The `mov rax, <value>` operand is always a decimal integer produced by `emit_dec`. Negative numbers are emitted as their two's-complement decimal representation.

## `lstr` Variables

Long strings are placed in `.data` rather than `.bss` because they carry a known initialiser. The layout is an 8-byte length field followed by the raw content bytes, each written as a decimal value to avoid quoting issues.

```nasm
section .data
v_greeting:  dq 5
    db 72,101,108,108,111
section .text
```

The length is stored as a plain `dq` (8 bytes, little-endian in memory). The `rt_lstr_idx` runtime helper reads it with a simple `mov rax, [rcx]` where `rcx` points to the label. An `lstr` with no initialiser defaults to the single character `'0'` (length 1, one byte of value 48).

<Note>
  Unlike `str` variables, `lstr` variables have **no** initialisation code in `.text`. The full content is baked into `.data` at assemble time. The runtime helper `rt_lstr_idx` addresses the bytes directly as `[rcx + rdx + 8]`, where 8 skips the length prefix.
</Note>

## `list` Variables

Lists are declared in `.bss` as a contiguous block of `LIST_CAP + 1` qwords (1025 × 8 = 8200 bytes per list). The first qword holds the current count; the remaining `LIST_CAP` (1024) qwords hold the entries.

```nasm
section .bss
v_scores:  resq LIST_CAP + 1
section .text
```

Because `LIST_CAP` is defined in the header boilerplate, this `resq` expression assembles correctly in the generated file. List entries are always 64-bit values: numbers are stored directly; short strings are packed little-endian into a qword in the same way as `str` variables.

<Warning>
  Lists cannot hold `lstr` values. The maximum element count is `LIST_CAP = 1024`. Attempting to append or insert beyond that limit causes the generated program to exit with runtime code `0x201` (list full).
</Warning>

## Footer

`s_footer` is emitted immediately after the last compiled statement:

```nasm

    xor  ecx, ecx
    call ExitProcess
```

`xor ecx, ecx` clears the exit code register to zero before calling `ExitProcess`, ensuring a clean exit when the program reaches the end of `main`.

## Runtime Helper System

Runtime helpers are appended after the footer only when needed, controlled by the `rt_need` bitmask. Each helper is a self-contained subroutine. If `rt_need` is zero, `out_end` jumps directly to `out_flush` and the helpers are never written.

When at least one helper is needed, a shared preamble is emitted first that defines the two runtime error exits:

```nasm
rt_err_full:
    mov  ecx, 0x201             ; list is full
    jmp  rt_die
rt_err_range:
    mov  ecx, 0x202             ; index out of range
rt_die:
    and  rsp, -16
    sub  rsp, 32
    call ExitProcess
```

The nine individual helpers are then emitted in order, skipping any whose bit is clear:

<CardGroup cols={2}>
  <Card title="rt_str_len" icon="ruler">
    **Bit:** `RT_STR_LEN` (`0x001`)  
    Counts the non-zero bytes in a packed `str` qword by shifting right 8 bits at a time until the value is zero.  
    **Calling convention:** `rax` = packed str → `rax` = length.
  </Card>
  <Card title="rt_str_idx" icon="text-cursor">
    **Bit:** `RT_STR_IDX` (`0x002`)  
    Extracts the character at a given index from a packed `str` qword. Returns `rt_err_range` if the index ≥ 8 or the byte is zero.  
    **Calling convention:** `rax` = str, `rdx` = index → `rax` = character byte.
  </Card>
  <Card title="rt_lstr_idx" icon="magnifying-glass">
    **Bit:** `RT_LSTR_IDX` (`0x004`)  
    Reads one byte from an `lstr` by pointer. Returns `rt_err_range` if the index ≥ the stored length.  
    **Calling convention:** `rcx` = `&lstr`, `rdx` = index → `rax` = character byte.
  </Card>
  <Card title="rt_list_append" icon="plus">
    **Bit:** `RT_LIST_APPEND` (`0x008`)  
    Appends a value at the end of a list. Calls `rt_err_full` if the count has reached `LIST_CAP`.  
    **Calling convention:** `rcx` = list base, `r8` = value.
  </Card>
  <Card title="rt_list_insert" icon="arrow-down-to-line">
    **Bit:** `RT_LIST_INSERT` (`0x010`)  
    Inserts a value at a given index, shifting the tail up. Calls `rt_err_full` or `rt_err_range` as appropriate.  
    **Calling convention:** `rcx` = list base, `rdx` = index, `r8` = value.
  </Card>
  <Card title="rt_list_remove" icon="minus">
    **Bit:** `RT_LIST_REMOVE` (`0x020`)  
    Removes the entry at a given index, shifting the tail down. Calls `rt_err_range` if index ≥ count.  
    **Calling convention:** `rcx` = list base, `rdx` = index.
  </Card>
  <Card title="rt_list_get" icon="eye">
    **Bit:** `RT_LIST_GET` (`0x040`)  
    Reads the value at a given index. Calls `rt_err_range` if index ≥ count.  
    **Calling convention:** `rcx` = list base, `rdx` = index → `rax` = value.
  </Card>
  <Card title="rt_list_sort_num" icon="arrow-up-1-9">
    **Bit:** `RT_SORT_NUM` (`0x080`)  
    Sorts a numeric list in ascending signed order using insertion sort.  
    **Calling convention:** `rcx` = list base.
  </Card>
  <Card title="rt_list_sort_str" icon="arrow-up-a-z">
    **Bit:** `RT_SORT_STR` (`0x100`)  
    Sorts a string list in ascending alphabetical order using insertion sort. Uses `bswap` to put the first character in the most-significant byte for a single-compare lexicographic sort.  
    **Calling convention:** `rcx` = list base.
  </Card>
</CardGroup>

## Assembling the Output

After the compiler runs, the generated `.nasm` file can be assembled and linked with the standard NASM win64 toolchain:

```bash
nasm -f win64 script.nasm -o script.obj
link /subsystem:console /entry:main script.obj kernel32.lib
```

This produces a native Windows PE executable (`script.exe`) with no runtime dependencies other than `kernel32.dll`, which is always present on Windows.

<Note>
  The generated NASM is human-readable by design. Labels are meaningful (prefixed `v_` for variables, `rt_` for runtime helpers), values are expressed as decimal integers rather than raw hex, and a comment at the top of every generated file reminds you of the correct assemble command. You can read, modify, or extend the output before assembling it.
</Note>
