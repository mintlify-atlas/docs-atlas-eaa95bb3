The `import` statement lets you split a Nano project across multiple files and reuse code written by others without copying it by hand. When the compiler encounters an `import`, the intended behaviour is to read the named file and insert its contents at that exact point in the source, making imported identifiers available to every statement that follows. The search order, package naming conventions, and `.ns` reserved-name rules are all designed and parsed; however, code generation for `import` is still in progress — see the note below.

## Syntax

```text
import <name>
```

`<name>` is the file or module identifier, without a file extension for local files or as a URL path for remote packages:

```text
import mathutils
import github.com/example/nanolibs/vectors.n
```

## Intended Search Order

When you write `import mathutils`, the compiler is designed to look for the file in the following order:

<Steps>
  <Step title="Same directory">
    The compiler checks the directory that contains the file currently being compiled. This is the most common case for splitting a project into multiple `.n` files.
  </Step>
  <Step title="Defined directory">
    If a package search directory has been configured, it is searched next.
  </Step>
  <Step title="System PATH">
    The compiler walks the directories listed in the system `PATH` environment variable, allowing globally installed Nano packages to be imported by name alone.
  </Step>
  <Step title="GitHub URL">
    If the import name begins with a URL (e.g. `github.com/...`), the compiler will fetch the file directly from that remote location and compile it without requiring a manual download.
  </Step>
</Steps>

## GitHub Imports

The design allows importing source files directly from GitHub by providing the full URL path to the `.n` or `.ns` file:

```text
import github.com/example/nanolibs/strings.ns
import github.com/example/nanolibs/mathutils.n
```

Because the file would be fetched and inserted at compile time, a project shared on GitHub could be compiled by anyone without manually downloading its dependencies.

## Package Files (`.ns`)

Nano packages use the `.ns` file extension. Inside a `.ns` file, identifiers whose names begin with `__` (two underscores) are **reserved** for use by that package. Attempting to define a `__`-prefixed name outside of a `.ns` file raises `ERR_RESERVED_NAME` (error code 15).

```text
# vectors.ns  (a package file)
var num __x = 0
var num __y = 0
```

```text
# main.n
import github.com/example/nanolibs/vectors.ns
```

## Example: Local Multi-File Project

```text
# utils.n
var num PI = 3

# main.n
import utils          # utils.n would be inserted here
```

<Note>
  Import code generation is not yet implemented. The compiler currently emits a `; TODO: statement type 11` placeholder when it encounters an `import` statement, meaning no file is actually read or inserted at this time. The parsing infrastructure and intended search-order behaviour are described above for reference, but compiled output for `import` will be available in a future release. Do not rely on `import` producing any effect in the current compiler version.
</Note>

<Tip>
  For large projects, plan to organise reusable code into `.ns` package files. The `__` namespace prefix is reserved for package-internal variables, preventing name collisions with the files that will eventually import them.
</Tip>
